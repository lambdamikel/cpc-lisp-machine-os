Pocket Lisp

A Lisp computer for the pocket: a microcontroller, a color screen and a real keyboard, running CPC Lisp's dialect on a 32-bit core. It is in the spirit of the Microtronic Phoenix, but with a modern MCU, and it switches on to where you left off.

For Mike. Covers the hardware architecture, the software core, and a way to get there that proves each step before the next.

What it should be

  • The same Lisp as on the CPC. Common Lisp syntax, closures, format, loop, structures, the function editor and the compiler. A program written for CPC Lisp should run unchanged.
  • Room to work. Tens of thousands of cells instead of 5,000, and numbers that don't overflow at 16,383.
  • Instant on. Switch it off in the middle of a session; switch it on and your definitions are still there, like the Sharp and Casio pocket computers.
  • Color and a big screen. 480 × 320 pixels, 60 × 40 characters in the CPC's own 8 × 8 font, sixteen inks. It starts in the CPC's colors, yellow on blue.
  • A keyboard made for Lisp. Parentheses, Eval and completion on their own keys.
  • Hackable hardware. An expansion header for speech, MIDI and whatever comes next, like the Phoenix and the LambdaSpeak cards.

Others have done this

David Johnson-Davies' uLisp runs on most of the chips below, and his Lisp Badge is a pocket Lisp computer with its own keyboard and display. Pocket Lisp stands apart in four ways:

  • a much fuller Common Lisp: format with all its directives, the extended loop, defstruct, multiple values, handler-case, string streams;
  • a bytecode compiler, written in Lisp;
  • the full-screen function editor and the pretty-printer;
  • CPC compatibility, down to the sound: sound, envelopes and play as the CPC firmware times them.

Microcontroller

Chosen

RP2350B · Waveshare Core2350B

Two Cortex-M33 cores at 150 MHz, 520 KB SRAM, single-precision floats in hardware and a coprocessor for doubles. PIO handles the keyboard, display and sound, and you know it from LambdaSpeak 4. The module is LambdaSpeak 4's: an RP2350B with 48 GPIO, 16 MB flash and 8 MB PSRAM (chip select on GP47). You have two spares, so nothing needs buying for the MCU. Cheap and low on power.

The module has no USB socket and no buttons. It needs a carrier: see below.

For a 5–7″ screen, or WiFi

ESP32-S3

512 KB SRAM plus 8 MB PSRAM, two cores at 240 MHz. Its RGB LCD interface drives 800 × 480 panels with the picture in PSRAM; ready-made boards with 4.3″ to 7″ screens exist. WiFi and Bluetooth for a network REPL or file sync. It draws more power and is less predictable in timing.

If speed matters

Teensy 4.1 · STM32H7

Cortex-M7 at 480 to 600 MHz, 1 MB RAM. The fastest option, but dearer, hungrier, and more work to lay out.

The software core

The core is a new implementation in C of the design CPC Lisp already has (docs/design.md, docs/internals.md), widened to 32 bits. It is not a port of the Z80 code: that is about 30,000 lines written for 64 KB and bank switching. Running those Z80 images in an emulated Z80 would work from day one and is worth a weekend as a test of the hardware, but it keeps the 64 KB, the 15-bit numbers and the string-space squeeze.

What carries over unchanged

  • All the Lisp-defined library: lisp.lsp, lisp2.lsp, loop.lsp, lazy.lsp, farray.lsp, the demos. About 72 KB of text that becomes part of the image.
  • The compiler (compiler.lsp, 779 lines). The C VM takes the same bytecode, so the compiler doesn't change, and tools/bootstrap.py can still compile it at build time.
  • The regression tests (test/*.lsp, 43 of them) and their expected transcripts. A host build on Linux runs them in seconds, before there is any board.
  • The machine interface (mach/README.md: CON_, KEY_, VID_, GFX_, SND_, FILE_) becomes a C header, implemented once for the host and once for the board.

What is written anew

  • The core: reader, printer, eval with tail calls, special forms, GC. About 130 functions.
  • The 220 library natives (strings, format, the editors, files, graphics, sound) and the bytecode machine's 85 operations.

The GC stays mark-and-sweep with an iterative mark stack. It still scans the C stack conservatively, which keeps the natives simple: a native may hold Lisp values in its locals.

Speed, as an estimate to check: (fib 24) takes about six minutes interpreted on a CPC (from (fib 17)'s 13 seconds, 29 times the calls). A C interpreter on a 150 MHz Cortex-M33 should do it in about a second. Measured on a PC so far: (fib 25) in 30 ms interpreted, 23 ms compiled. The benchmarks in docs/benchmarks.md (fib, tak, deriv) will say on the board.

Getting there

  1. The core on Linux.Done. The C core in pocket/ runs the Lisp text unchanged and passes all 36 tests that need no CPC keys or screen.
  2. On a Core2350B on its carrier.The same core on the RP2350B, with the heap and M: in PSRAM and a USB serial REPL. Then the 4″ screen and a borrowed keyboard. Measure the benchmarks.
  3. The pocket parts.The keyboard matrix, the editor and structure editor on the screen, color graphics, files on microSD, the saved image, sound through the emulated AY.
  4. The compiler.Done on Linux. The bytecode VM in C, the compiler as it is: disassemble and compile-file give the CPC's bytes exactly. Next, compile-file on the device.
  5. A board and a case.A PCB with the module, keys, OLED, battery and header; a printed case.

Decisions for you

  • Screen size: decided: the 4″ 480 × 320 with the RP2350.
  • The module: decided: the Waveshare Core2350B, with 8 MB PSRAM.
  • Text modes: the three sizes above as (mode 0), (mode 1), (mode 2), with 60 × 40 at the start?
  • Keyboard: your own key matrix, or a ready-made BlackBerry-style module to start with?
  • Where it lives: decided: pocket/ in the CPC Lisp repository, sharing its Lisp text and tests.
